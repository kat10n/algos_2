# Разбор кода с доски и файлов препода

Полезно знать эти места: на контесте такие же ошибки дают WA/RE, а на защите домашки о них могут спросить.

## Доска 1: counting sort

```cpp
int m = mx - mn;
vector cnt(m, 0);
```
1. **Размер на 1 меньше нужного.** Значения после сдвига лежат в `[0, mx - mn]` — это `mx - mn + 1` штук.
   Максимальный элемент обратится к `cnt[m]` — выход за границу (UB: может упасть, может молча испортить память).
   Правильно: `vector<int> cnt(mx - mn + 1, 0);` и в префиксных суммах `i < m + 1`.
2. **Сдвиг не возвращается.** `a[i] -= mn` меняет входной массив, а в `ans` попадают сдвинутые значения.
   Для `a = {5, 7, 6}` вернётся `{0, 1, 2}`. Нужно либо `ans[...] = a[i] + mn`, либо не трогать `a`
   и считать индекс как `cnt[a[i] - mn]` (так в `03_counting_sort.cpp`).
3. **`const` над параметром** (пометка стрелкой) — идея правильная, но с `a[i] -= mn` не скомпилируется.
   Если не менять `a` (п.2), то `const vector<int>& a` — лучший вариант.
4. **Пустой массив:** `*max_element` от пустого диапазона — UB. Нужен `if (a.empty()) return {};`.

## Доска 2: radix sort

1. `const exp` без типа — не компилируется в C++ (нет "неявного int"). Нужно `long long exp`.
2. `for (int exp = 1; mx / exp > 0; exp *= 10)` — при `mx ≥ 10⁹` на последнем шаге `exp = 10⁹ · 10`
   переполняет `int` (UB). Используй `long long exp`.
3. Работает **только для неотрицательных**: у отрицательного `(a[i] / exp) % 10` отрицателен → `cnt[-3]`.
   Решение: сдвиг на минимум или трюк со знаковым битом (`04_radix_sort.cpp`, п.3).

## Файлы препода

**Переносимость типов (`size_t` vs `uint64_t`).** `CountingSort` принимает `vector<uint64_t>&`,
а `main.cpp`/`test.cpp` передают `vector<size_t>`, и внутри `vector<size_t> result` присваивается в `a`.
На Linux x86-64 оба типа — `unsigned long`, всё компилируется. На macOS `size_t = unsigned long`,
а `uint64_t = unsigned long long` — это **разные типы**, будет ошибка компиляции. Лучше везде один тип.

**`ssize_t`** — это POSIX, а не стандарт C++. В MSVC (Visual Studio) его нет. Для обратного цикла
проще `for (int i = n - 1; i >= 0; --i)`.

**`counting_sort.cpp`:** массив `cnt` размера `maxElem + 1` без сдвига на минимум. Для чисел до 10⁹
это 8 ГБ памяти — об этом и комментарий в бенчмарке. Плюс нет поддержки отрицательных.

**`counting_sort.h`:** нет `#pragma once` (защиты от двойного подключения). Пока один `#include`, не страшно.

**`lsd_sort_2.cpp`:**
- название «2», но основание `2^8 = 256`; в комментарии к сложности тоже написано «основание 2» — на самом деле `k = 256`.
- `MASK = ELEMENTS - 1; // 0x1111111` — комментарий неверный: `255 = 0xFF = 0b11111111`.
- нет `#include <vector>` и `#include <array>` — компилируется только за счёт того, что их подключит кто-то ещё.
- `result = buffer;` копирует весь массив на каждом проходе (O(n) лишней работы). `result.swap(buffer)` — O(1).

**`lsd_sort_10.cpp`:** `GetIthDigit` делает `i` делений — препод это отметил, в `_optimized` исправлено
через `divider`. В обоих то же лишнее копирование `result = buffer`.

**`bencmark.cpp` для LSD:** подключает `lsd_sort.h`, которого нет среди файлов; нет `#include <limits>`
для `numeric_limits`. Отрицательные `int` из генератора превращаются в огромные `uint64_t`
(`-1 → 18446744073709551615`) — сортировка всё равно корректна, но для LSD по основанию 10
это до 20 проходов вместо ~10.

**`external_sort.cpp`:**
- `generator.py` пишет первой строкой `n`, а сортировка читает его как обычный элемент — в ответе окажется лишнее число
  (в NOTE это признаётся; в `06_external_sort.cpp` есть флаг `firstIsCount`).
- для последнего (неполного) куска не проверяется `is_open()`; если папки `./data/tmp` нет, данные молча не запишутся.
- `std::runtime_error` без `#include <stdexcept>`, временные файлы не удаляются.
